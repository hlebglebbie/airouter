# airouter

OpenAI-совместимый роутер LLM с автофейловером, веб-интерфейсом и Telegram-ботом для добавления ключей. Один endpoint раздаёт две виртуальные модели — `fast` (быстрая) и `think` (умная) — и сам выбирает лучший из подключённых upstream-API по замерам скорости и размеру модели.

## Возможности

- OpenAI-совместимый endpoint: `/v1/chat/completions` и `/v1/models` (поддержка `stream`).
- Две виртуальные модели: `fast` → самый быстрый провайдер, `think` → самая крупная модель (по эвристике имени).
- Автоматическая проверка провайдеров: `/models` + тестовая генерация с замером задержки.
- Фейловер: при ошибке сразу переключается на следующего кандидата; «упавшие» провайдеры проверяются раз в 60 секунд и возвращаются в ротацию.
- Ручной выбор модели для каждого виртуального маршрута.
- Веб-дашборд на `/` для управления провайдерами, замерами и маршрутизацией.
- **Telegram-бот**: пересылаете боту сообщение с ключами — он вытаскивает их и base URL и добавляет провайдеров. Токен бота настраивается в дашборде, без правки конфигов и рестарта.
- **Прокси для Telegram API** через [free-proxy](https://pypi.org/project/free-proxy/): нужно, когда `api.telegram.org` недоступен напрямую.
- Сохранение настроек в `providers.json` (переживает рестарт).

## Быстрый старт

```bash
./dev/run.sh
```

Скрипт собирает сервер, поднимает его, ждёт готовности `/healthz` и запускает бота. При первом запуске бота он создаёт `.venv` и ставит зависимости из `bot/requirements.txt`. `Ctrl+C` останавливает оба процесса; если один из них умирает, второй тоже гасится.

Флаги: `--release` (release-сборка), `--no-bot` (только сервер).

Требуется Rust (stable), Python 3.11+ (столько требует актуальный aiogram), curl. Ручная сборка без скрипта:

```bash
cargo build --release
./target/release/airouter
```

Сервер слушает `http://127.0.0.1:5959` — откройте этот адрес в браузере, там веб-интерфейс.

## Telegram-бот

Бот нужен только для того, чтобы добавлять провайдеров пересылкой сообщения в чат. Без него роутер работает полностью — провайдеров можно добавлять через дашборд или Admin API.

**Настройка.** Откройте дашборд → вкладка «API» → раздел «Telegram-бот» → вставьте токен от [@BotFather](https://t.me/BotFather) и нажмите «Сохранить». Он пишется в `providers.json`; бот опрашивает сервер раз в 10 секунд и подхватывает изменение сам, перезапуск не нужен. «Отключить» убирает токен, бот засыпает и ждёт нового.

**Что делает бот с сообщением.** Из произвольного текста — проза, эмодзи, Markdown, репосты из каналов — он выдёргивает ключи и ссылки и сопоставляет их друг другу:

```
репост 👇 https://t.me/mychannel
**https://api.samp.team/v1**
ключ `sk-EACv…xzqD` — рабочий, проверено ✅
```

→ добавлен провайдер `api.samp.team` с base URL `https://api.samp.team/v1`.

Правила разбора (`bot/keyparser.py`, чистый stdlib):

- Ключ — `sk-` и минимум 20 символов после него. Покрывает `sk-cp-81-…`, `sk-50x-…`, `sk-ant-…`; обрезки вроде `sk-not-a-real-key` отбрасываются.
- Base URL принимается со схемой (`https://api.foo.com/v1`) и без неё (`api.foo.com/v1`); суффиксы эндпоинта срезаются до базы (`/v1/chat/completions` → `/v1`), query и fragment отбрасываются, хвостовая пунктуация и Markdown-обрамление убираются.
- Ссылки на доки, соцсети и трекеры (`t.me`, `github.com`, `discord.gg`, `habr.com` и др.) не рассматриваются как база — ключ на них не повесится.
- Каждому ключу достаётся ближайшая API-ссылка до него, затем после него, затем любая пригодная ссылка. Если ссылки в сообщении нет вовсе — ключ не добавляется, бот назовёт его и попросит прислать base URL.
- Имя провайдера в дашборде — хост эндпоинта.

**Прокси.** По умолчанию бот берёт прокси из free-proxy и ходит через него к `api.telegram.org`. Бесплатные прокси недолговечны и нередко оказываются мёртвы или MITM'ят TLS, поэтому бот ротирует их: каждый цикл — новый прокси и новая сессия, после ошибки свежий прокси берётся через 1 секунду, и только после пяти подряд неудач — пауза 15 секунд. Ошибки токена от сбоев прокси отделены: неверный формат или 401 останавливают ротацию и печатают внятное сообщение, а не крутят узлы бесконечно.

Если бот должен ходить напрямую (или через свой прокси) — задайте переменную окружения при запуске:

```bash
TG_PROXY=off ./dev/run.sh                      # напрямую
TG_PROXY=http://user:pass@host:3128 ./dev/run.sh  # свой прокси
TG_PROXY_COUNTRIES=DE,NL ./dev/run.sh          # фильтровать по странам
```

Запросы к локальному airouter идут мимо прокси отдельной сессией — ключи не уходят через чужие узлы.

## Использование endpoint

Клиент указывает `base_url = http://127.0.0.1:5959/v1` и модель `fast` или `think` (принимаются алиасы `gpt-fast`, `gpt-think` и др.).

```bash
curl http://127.0.0.1:5959/v1/chat/completions \
  -H 'Content-Type: application/json' \
  -d '{"model":"fast","messages":[{"role":"user","content":"привет"}],"stream":false}'
```

## Добавление провайдера

Через веб-интерфейс, Telegram-бота или API:

```bash
curl -X POST http://127.0.0.1:5959/api/providers \
  -H 'Content-Type: application/json' \
  -d '{"name":"my-api","base_url":"https://api.example.com/v1","api_key":"sk-...","model_override":null}'
```

Можно добавить несколько ключей одного сервиса — каждый отдельной записью; роутер сам переключится на рабочий. Дедупликации нет: одно и то же сообщение, отправленное дважды, создаст двух одинаковых провайдеров — лишнего удаляйте вручную через «Удалить» в дашборде.

## Admin API

- `GET /api/state` — состояние провайдеров и маршрутов (+ `telegram`)
- `POST /api/providers` — добавить провайдера
- `PUT /api/providers/{id}` / `DELETE /api/providers/{id}` — изменить / удалить
- `POST /api/providers/{id}/check` / `POST /api/check_all` — перепроверить
- `POST /api/benchmark` — запустить «забег скорости»
- `PUT /api/routing` — выбрать модель для `fast` / `think`
- `PUT /api/telegram` — задать или сбросить токен бота (`{"token": "..."}`, пустая строка = отключить)
- `GET /api/telegram/token` — сырой токен для бота; только для localhost

## Переменные окружения

| Переменная | Для | По умолчанию | Значение |
| --- | --- | --- | --- |
| `AIROUTER_DATA_FILE` | сервер | `providers.json` | путь к файлу настроек |
| `AIROUTER_URL` | бот | `http://127.0.0.1:5959` | адрес airouter |
| `TG_REFRESH_SECS` | бот | `10` | как часто проверять смену токена |
| `TG_PROXY` | бот | `auto` | `auto` (free-proxy) · `off` (напрямую) · URL прокси |
| `TG_PROXY_COUNTRIES` | бот | все | страны через запятую, например `DE,NL` |
| `TG_PROXY_ROTATE` | бот | `300` | срок жизни прокси, сек; `0` — без ротации |
| `TG_PROXY_FALLBACK_DIRECT` | бот | выключено | `1` — если прокси не достался, идти напрямую |

## Тесты

```bash
cargo test                     # тесты сервера
python3 bot/test_parser.py     # проверки разбора ключей и base URL
```

Оба раннера печатают своё количество проверок. Тесты парсера не требуют зависимостей — только stdlib, запускаются системой `python3`.

## Структура

```
src/                    сервер (axum): proxy, admin, benchmark, state, intel, upstream
static/                 дашборд (HTML/CSS/JS, вшивается в бинарь через include_str!)

bot/keyparser.py        разбор ключей и base URL из текста
bot/test_parser.py      его тесты (печатают своё количество)
dev/run.sh              поднять сервер и бота вместе
dev/upstream_stub.py    мок-upstream для ручной проверки фейловера
providers.example.json  шаблон файла настроек
```

## Безопасность

Сервер слушает только `127.0.0.1`. Три момента, которые стоит знать перед пробросом порта наружу:

- **API-ключи** лежат в `providers.json` в открытом виде — не коммитьте этот файл (он уже в `.gitignore`) и не открывайте порт без reverse-proxy с аутентификацией.
- **`GET /api/telegram/token`** отдаёт токен бота без авторизации. Пока сервер на localhost — безопасно; при пробросе порта этот маршрут нужно закрыть.
- **Бот принимает сообщения от всех.** Whitelist по `chat_id`/`user_id` не реализован: любой, кто узнает имя бота, сможет добавить ключи в ваш роутер. Держите имя бота приватным или добавьте фильтр в `bot/tg_bot.py` (`on_text`) перед тем, как давать боту публичное имя.

Сам бот ходит к Telegram через случайные бесплатные прокси. Содержимое запросов они не читают (трафик внутри TLS-туннеля, сертификат проверяется по `certifi`), но видят хост и тайминги. Для продакшена поставьте свой проверенный прокси через `TG_PROXY`.
